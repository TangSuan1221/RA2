## 0. 摘要

### 0.1 五条结论

1. **交互物是「少量原型 + 参数化变体」，不是每个都是独特组件。** TLOU2 的场景是模块化 prefab 装配，交互语义由「几何 + 触发体积 + 状态机 + native 调用」组成（E2，见 [S1]）。
2. **真正需要硬尺寸的约 20 类。** 通行、门窗、梯绳、攀爬辅助、关键设施、载具、掩体是硬规范；拾取物、容器、装饰、可破坏物只需范围；触发体积、AI 标记、光源不需要美术尺寸。
3. **所有硬尺寸都围绕三组锚点。** 玩家 1.80m、胶囊 0.32–0.38m；垂直分层 0.45/1.20/2.20m；门洞 0.9×2.1m。离开这三组锚点谈尺寸没有意义。
4. **TLOU2 的「跳跃」是上下文跳跃，不是自由物理跳。** 从可观测行为看，最合理的工程实现是「通行链接（link）+ 定制 montage」，而不是通用物理跳跃。这决定了它适合组件化，但不适合用一套动画覆盖所有间距（E3 推断）。
5. **尺寸一致性按「族」管理，不按「全局唯一值」管理。** 同族窗户的洞口、窗台、墙厚、marker 必须一致；不同族可以不同；窗框外形可以自由。

### 0.2 数量级

| 统计项 | 数值 | 来源 |
|---|---|---|
| 可归类交互机制 | 约 **60–70 类**（含子类） | 本文归类 |
| 需要硬尺寸（S） | 约 **20 类原型**，展开为 **50+ 子类型** | 本文判定 |
| 只需范围（R） | 约 **25 类** | 本文判定 |
| 无需美术尺寸（N） | 约 **10 类** | 本文判定 |

| 工作台 | **25** | E2，[S16] |

本仓库 REA 已给出 15 类交互物框架；本文按可见机制扩展到 60–70 类，并给每一类加尺寸等级。

### 1.2 证据分级

| 等级 | 含义 | 本文用法 |
|---|---|---|
| **E1** | 一手：官方文档、GDC 演讲、工具源码直接证实 | 只用于「机制存在」「格式结构」；不用于具体米数 |
| **E2** | 可观测：游戏内可见、攻略/社区一致、截图可验证 | 交互物清单、按键、数量、位置 |
| **E3** | 工程估算：按玩家尺度、真实建筑标准、关卡度量反推 | 所有尺寸规范、公差、范围 |

### 1.3 局限（必须先读）

- **没有官方尺寸表。** 网上能查到的门、窗、梯子尺寸，绝大多数是玩家估算或现实建筑标准，不是 Naughty Dog 的内部数值。
- **攻略只证明「存在」，不证明「多大」。** 例如「这里有一架梯子」是 E2，「梯子宽 0.5m」是 E3。
- **逆向工具能导出模型，但公开资料没有汇总尺寸。** aluigi 的工具能拿模型和骨骼（[S27]），`nd_pak.bt` 能读 pak 结构（[S28]），但没有一份「TLOU2 prefab 尺寸表」可直接下载。
- **数量也有分歧**：工作台各攻略有 23/24/25 三种说法，本文取 25；以游戏内奖杯/存档统计为准。
- **因此**：清单是 E2，尺寸是 E3；落地前必须按 §7 实测。

### 1.4 开源 / 逆向工具链（能拿到什么，拿不到什么）

| 工具 | 能做什么 | 不能做什么 |
|---|---|---|
| `TLOU_PSARC_Tool` / `U4.PSARC.Tool` | 解包/重打包 psarc | 不给尺寸表 |
| `fmt_nd_pak` / `nd_pak.bt` | 读 pak 内部结构（GEOMETRY/JOINT/TEXTURE） | 不给尺寸表 |
| aluigi TLOU2 tool（[S27]） | 导出模型、骨骼、贴图 | 不给尺寸表 |
| `dconstruct`（[S29]） | DC 脚本反汇编/反编译 | 不给尺寸表 |
| `ndmodloader`（[S30]） | 加载自定义 psarc | 不给尺寸表 |

**结论**：开源工具能让你**拿到 prefab 并自己量**，但没有任何一个工具附带「TLOU2 交互物尺寸数据库」。所以 §7 的测量协议不是可选项，是必做项。

## 7. 从 E3 到 E1：测量协议

这是把本文的估算变成你自己项目「硬数据」的唯一路径。方法沿用 REA 报告的 prefab 直方图法（[S1] §3.6）。

1. **解包**：用 `nd_pak.bt` / `fmt_nd_pak` 读 pak（[S28][S32]），或用 aluigi 的 TLOU2 工具导出模型/骨骼（[S27]）。
2. **导入**：Blender / Noesis 导入同类 prefab（窗、门、梯、掩体）。
3. **量净尺寸**：量**净洞口**、窗台高、上沿高、墙厚、落脚深度，不要量外框装饰。
4. **做直方图**：同类量 20–30 个，尺寸直方图的尖峰就是引擎标准值；离群值剔除。
5. **校准玩家**：以角色模型/官方设定身高（约 1.80m）为初值，用门、台阶、掩体的截图比例交叉校验；不要用本文的门高反过来证明本文的门高。
6. **跑测试**：角色从 entry 到 exit 播 montage，落点误差 ≤0.15m；AI 胶囊从同一洞口通过。
7. **写回规范**：把实测值写进 `prefab-spec.json`，导入时自动校验；超过公差就拆族。

> 没有这一步，本文所有尺寸都只是「设计建议」，不是「你的项目标准」。

### 8.2 尺寸管理

- **按族建 spec**：`window_A`、`window_B`、`door_A`、`ladder_A`……同族共享尺寸与 marker。
- **同族硬规范，异族可不同**：不要为了「统一」把所有窗做成一个尺寸；也不要为了「多样」让同族窗乱跳。Teletype 的关卡分析也指出：同类掩体高度必须收敛，否则玩家无法凭直觉分类（[S24]）。
- **外形自由，接口固定**：窗框、窗棂、玻璃、破损可以变；净洞口、窗台、墙厚、marker 不能变。
- **公差三档**：通行关键 ±0.03m；大型构件 ±0.05m；道具 ±10%。
- **导入即校验**：prefab 导入时检查 marker、洞口、碰撞洞、LOD、预算；不合格直接拒绝。

### 8.3 900×700 版 vs 4096m 版

| 项目 | 900×700 版 | 4096m 版 |
|---|---|---|
| 垂直分层 | 0.45/1.20/2.20m | 同左 |
| 门洞 | 0.90×2.10m | 同左 |
| 单人净宽 | 1.20m | 1.20m |
| 道路宽度 | 4/5/7.5/10/14m | 6–10/12–20/24–36m |
| 缝隙矩阵 | 0.6/1.0/2.5/3.5 | 同左 |
| 视线断点 | 8–12m | 8–12m |
| 流送单元 | 街区（110m 级） | 32m chunk |
| 地形 | 标高台地/坡道 | 高度场 |

### 8.4 不要做的事

- **不要给每个窗户写独立脚本。** 用族 + 参数 + montage tag。
- **不要把 unique set-piece 强行通用化。** 断桥跳跃可以复用 link，但动画可以定制。
- **不要用 AABB 做斜放家具的碰撞。** 用 OBB/凸包，否则会出现看不见的直角墙。
- **不要直接抄本文的米数。** 本文是 E3；你的角色、胶囊、动画不同，必须按 §7 校准。
- **不要用模型外框量尺寸。** 量净洞口，否则碰撞洞和视觉洞口会打架。

## 一句话总结

> **TLOU2 的交互物不是「每个都是独特组件」，而是「少量原型 + 参数化变体 + 族级尺寸规范」。真正需要硬尺寸的只有通行、门窗、梯绳、关键设施、载具、掩体这六类；其余用范围或无尺寸。所有数值都是 E3，落地前必须用 prefab 直方图法和 traversal 测试校准成你自己的 E1。**
